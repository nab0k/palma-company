# Stream 2 — Evidence status

combination or naming, built on but not identical to the adjacent theory);
observed case evidence (an actual, source-carded instance exists);
retrospective interpretation (a case was read through this field after the
fact, not tested prospectively); untested causal proposition (the field

## Does each field's cited source actually support it, or was a source stretched?

Checked directly against this task's own instruction not to stretch a
source to cover a construct it did not study:

- **Roles → Wenger**: supports. Wenger's own subject matter (roles within
  a community of practice, legitimate peripheral participation) is
  substantively the field being described. No stretch.
- **Rhythms → Feld** (as currently credited in the Prior Art Matrix):
  **a mild stretch.** Feld's theory is about *opportunity structures*
  (foci) that make encounter more likely — closer to Channels' or Routes'
  subject matter than to a recurring cadence per se. Chapter 13's own text
  correctly grounds "rhythm" in Collins instead. Recommend the Prior Art
  Matrix's Canvas row be corrected to credit Collins for Rhythms
  specifically in any future revision (not made in this task, since that
  file is outside this task's declared output paths).
- **Channels → Feld/Wenger**: supports, reasonably. Both theories concern
  where and how repeated contact becomes possible; this is close to a
  direct match.
- **Routes → Feld**: **a real stretch**, more serious than the Rhythms
  case above. Feld's foci are about *shared context that allocates
  opportunity for encounter generally* — not about a specific,
  nameable person-to-person path that can be used without a broker, which
  is what "Routes" as defined in the Tool Spec actually asks a
  practitioner to identify. Recommend this attribution be reconsidered in
  any future revision — not made in this task.
- **Memory → (none, prior to this task)**: did not exist; not a stretch,
  a genuine absence, now partly closed by SC-119 at the "checked, not
  verified" tier only.

## Why no other new source card was created in this task

Routes, Rhythms, and Channels each already have a real, checkable
predecessor (even where the specific attribution could be sharpened, as
noted above) — creating a further card for any of them would duplicate
existing, adequate coverage. Roles is well covered by Wenger. Only Memory
had a genuine, total absence of theoretical grounding, which this task
closed with one properly bounded, honestly labeled card (SC-119) rather
than stretching Ostrom, Selznick, or Wenger to cover a construct none of
them actually studied — consistent with this task's explicit instruction.

# Stream 4 — Operational specification options

Two options are presented, per the task's instruction not to silently
select one. Neither changes the canon, a decision, or the manuscript;
both are drafted for Founder or Chief Editor review.

## Option A — Retain and strictly define the five fields

**Construct definition.** The Infrastructure Canvas remains a five-field
decision sheet (Routes, Roles, Rhythms, Channels, Memory), unchanged in
name and count. Each field's definition is tightened only enough to remove
the specific drifts found in Stream 1 — principally, Routes is restricted
to its social sense only (no literal/geographic reading permitted), and a
mandatory discriminant check is added between Routes and Channels.

**Unit of analysis.** Unchanged: one bounded intervention, function, or
observation window, per the existing Design-stage completion criteria in
`PALMA_METHOD_TOOL_SPEC_v0.2.md`.

**Blank template (revised instructions, same five fields):**

```
Routes — name the specific person(s) who form the path from one
  participant to another. If your answer is a place, app, or group name
  rather than a person, you have described a Channel, not a Route — fill
  Channels instead and leave this blank until you can name a person.
Roles — what will a participant be able to DO here, beyond receiving a
  service or watching? Name the action, not a job title.
Rhythms — what repeats on its own schedule, without a fresh invitation
  each time? Name the specific recurring event, not a general cadence.
Channels — name the shared medium (a place, app, or recurring format)
  more than one route could use. Existence and membership count are not
  evidence by themselves — name how you would check whether it is used
  without the organizer present.
Memory — what will a returning or new participant not have to be told
  again? Optionally, name which of Walsh & Ungson's five retention bins
  (individual, culture, transformations, structure, ecology) it lives in —
  a fill naming only the individual bin is a center-dependence signal,
  not a pass.
```

**Fill order.** Roles and Rhythms first (best-evidenced, least ambiguous);
Channels next; Routes only after Channels is filled, explicitly checking
against it (per the template above); Memory last, since it depends on the
other four having already produced something worth remembering.

**Decision rule.** Design is complete only when Routes and Channels
contain genuinely different content (not the same fact restated) — this
becomes a sixth, explicit completion check alongside the five already in
`PALMA_METHOD_TOOL_SPEC_v0.2.md`'s Design-stage criteria.

**Falsification rule.** A field is "real" only when its own observable
sign is met AND the practitioner has recorded at least one specific,
dateable instance — a general impression never counts, consistent with
the existing standard already applied to Response Signals and the
Relationship Capital Map. Additionally, per Stream 3's Case D finding: a
field being "real" by its own test does not certify that the Method's
deeper outcome (a Response Signal, a Palma Moment) will follow — this
should be stated explicitly in the tool's own instructions, not left
implicit.

**Status language safe for the book.** "A five-field decision sheet built
on established adjacent research (Wenger for Roles; Collins for Rhythms;
Feld and Wenger for Channels; Walsh and Ungson for Memory), not itself an
independently validated instrument. Two of the five fields (Routes and
Channels) require active discrimination during use, per the tool's own
instructions, because their subject matter is genuinely close." This is
more honest, and more defensible under scrutiny, than the current
"five fields... do not erase Chapter 13's wider vocabulary" language alone.

**Effect on existing material:**

- *Chapter 13*: no change to the six design elements; a possible future
  footnote-level cross-reference is not required by this option.
- *Chapter 18*: the retrospective TAK.Shtab Canvas fill needs a rewrite
  bounded to a single window (see Stream 3, Case A) — a manuscript
  editing task, not authorized or performed here.
- *Appendix 1*: section 4's five-field description needs the tightened
  Routes definition and the Routes/Channels discrimination instruction
  added.
- *Scientific note (Appendix 2 / Field Guide)*: needs one added sentence
  naming Memory's new theoretical anchor (SC-119) at the "checked, not
  verified" tier — not "validated."
- *Canon v1.1*: no change required; the Canon's existing one-line
  description of each field remains compatible with tightened Tool Spec
  language, since the Canon does not currently define the fields in
  enough detail to conflict.
- *DECISION_0006*: no change required; DECISION_0006 names the tool, not
  the field-level definitions.

## Option B — Revise the field structure

**Construct definition.** The Canvas becomes a four-field decision sheet:
**Access** (merging Routes and Channels into one field with two required
sub-answers — "who" and "where/what medium" — rather than two separate
fields that keep converging on the same fact), **Roles**, **Rhythms**
(with an added, explicit sub-question about whether repetition happens
with a consistent group of people or a rotating one — see the missing-
construct finding below), and **Memory** (unchanged in name, newly
anchored to Walsh & Ungson, still flagged as the weakest field).

**Missing-construct finding motivating this option.** Stream 3's Case D
(the TCF low-regularity member) shows that Rhythms, as currently defined,
is satisfied by mere repetition — the member returns weekly without a
fresh invitation — while the actual mechanism her own account identifies
as necessary is repetition *with the same specific people*, not raw
frequency. None of the five current fields asks whether a rhythm's
participants are consistent or rotating. This is not adequately captured
by adding a sixth field (which would worsen, not fix, the tool's already-
documented complexity and vocabulary problems); it is better captured as
a required sub-question inside Rhythms.

**Unit of analysis.** Unchanged from Option A.

**Blank template:**

```
Access — (a) name the specific person(s) who form the path between two
  participants; (b) name the shared medium, if any, that path uses. If
  you cannot answer (a) with a person's role or name distinct from your
  answer to (b), you do not yet have a confirmed route — you have only a
  channel, which is a necessary but not sufficient condition.
Roles — unchanged from Option A.
Rhythms — what repeats on its own schedule? AND: does it repeat with a
  consistent group of the same people, or a rotating/anonymous one? Per
  this project's own case evidence (SC-099), the second question, not the
  first, is what predicts whether repetition produces connection.
Memory — unchanged from Option A, including the optional five-bin check.
```

**Fill order.** Roles and Rhythms (both sub-questions) first; Access
second, explicitly building on whatever channel Rhythms already named;
Memory last.

**Decision rule.** Design is complete when Access's two sub-answers are
genuinely distinct from each other and Rhythms' second sub-question has
been answered explicitly (not left as an unstated assumption of "yes, the
same people," which Stream 3's Case D shows cannot be assumed).

**Falsification rule.** Same as Option A, applied to four fields instead
of five; the Access field's own internal (a)/(b) discrimination replaces
the cross-field Routes/Channels discrimination Option A requires.

**Status language safe for the book.** "A four-field decision sheet,
revised from an earlier five-field version after an internal audit found
two of the five fields (Routes and Channels) could not be filled
independently in practice. Built on established adjacent research
(Wenger for Roles; Collins for Rhythms; Feld and Wenger for Access; Walsh
and Ungson for Memory)." This status language requires disclosing that a
revision occurred — a Founder/Chief Editor call, not made here.

**Effect on existing material:**

- *Chapter 13*: no change to the six design elements themselves, but the
  crosswalk table in `INFRASTRUCTURE_CANVAS_INTERNAL_AUDIT_v0.1.md`
  (Finding F4) would need to be re-derived for four fields instead of
  five — Access absorbs both Channel and (implicitly) part of what
  Chapter 13 calls Channel; Rhythms absorbs a sharper version of Chapter
  13's Ritual question ("does repetition still mean something to the
  people repeating it," which is adjacent to, though not identical with,
  "is it the same people repeating it").
- *Chapter 18*: the TAK.Shtab worked example would need a full rewrite
  under the new four-field structure, in addition to the period-bounding
  fix Option A also requires — a larger manuscript-editing task.
- *Appendix 1*: section 4 would need the most substantial rewrite of any
  file affected by either option, since it currently presents five fields
  as a flat, parallel list.
- *Scientific note*: would need a new paragraph explaining the revision
  itself (what changed, why, and that four fields supersede five, per
  this repository's append-only, non-silent-replacement rule) —
  more disclosure than Option A requires.
- *Canon v1.1*: **would require a formal amendment or addendum**, since
  the Canon currently names the tool as having "routes, roles, rhythms,
  channels, memory" explicitly, five named fields — Option B directly
  changes what a Founder-approved document states. This is the most
  consequential difference between the two options: Option A can be
  implemented via Tool Spec and manuscript edits alone; Option B cannot,
  without first touching the Canon.
- *DECISION_0006*: no direct change required (DECISION_0006 does not
  itself enumerate the five field names — Canon v1.1 does), but the
  practical effect is the same increased-disclosure burden as the Canon
  amendment above.

## This audit's position

Per the task's own instruction, this audit does not select between Option
A and Option B — that is a Founder or Chief Editor decision. Both options
are internally consistent with the evidence in Streams 1 through 3. Option
A is the lower-disruption path and directly available without a Canon
change; Option B more fully closes the gaps this task found (including
the Rhythms sub-question Option A does not address) but requires the
Founder to accept a disclosed revision to an approved document (Canon
v1.1) and a larger manuscript-editing task. Either option should be
converted into a formal decision-options memo for `DECISIONS.md` before
any manuscript or Canon file is touched, per AGENTS.md's editing gates.

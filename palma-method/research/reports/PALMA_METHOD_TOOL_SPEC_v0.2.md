# Palma Method — tool specification v0.2

Editorial working document. Not manuscript prose. Revises v0.1 per explicit author
direction: tighter stage-completion criteria, a two-layer Relationship Capital Map,
a nonlinear Response Signals set replacing the linear ladder, a more careful Palma
Moment definition, a Handoff Test without a fixed window, and stricter discipline
against generalizing single TCF interviews into laws.

## Architecture

**Diagnose → Design → Launch → Transfer.** **Facilitate** operates across all four
stages as a cross-cutting principle, not a fifth sequential stage — see the
dedicated section after the four stages below. (This principle was called
"Advise/Facilitate" in v0.1; this version uses the author's preferred single name,
**Facilitate**, throughout.)

Book architecture this spec assumes, per current author direction: Chapters 1-10
teach the reader to see Relationship Capital; Chapters 11-16 give discrete practices
(listening, mapping, hypothesis, participation, measurement, ownership); Chapters
17-21 assemble those practices into a sequential Palma Cycle on the TAK.Shtab
throughline; Chapter 20 is a Facilitate interlude, not a stage; a separate
conclusion is still needed after Chapter 21.

---

## Stage 1 — Diagnose

**Stage question**: What is actually missing here, at what unit of analysis, and
what evidence would prove this diagnosis wrong?

**Input**: a stated problem, in the client's or practitioner's own words, plus
whatever informal observation is already available.

**Actions**: name the presenting problem; state explicitly which unit of analysis
it concerns; ask what alternative explanation would also fit the same facts; check
whether the diagnosis survives being applied to a narrower or wider unit.

**Concrete artifact**: a **Relationship Capital Map** entry — a written diagnosis
with all five of the following named:

**Diagnose is complete when, and only when:**

1. a specific problem has been named (not a category — "reach isn't converting"
   is not specific; "this class-time slot doesn't reconnect returning members
   with anyone" is);
2. the unit of analysis is fixed and stated — a single tie, a subgroup, a network,
   or the whole organization — because each produces a different, non-interchangeable
   diagnosis;
3. an observable bottleneck has been identified — something that can actually be
   pointed to, not inferred from mood;
4. an alternative explanation has been formulated and named, even if it is then
   set aside;
5. it is stated what data would falsify this diagnosis — what observation, if it
   occurred, would mean the diagnosis is wrong.

**Typical mistakes**: premature closure (stopping at the first plausible
explanation); diagnosing at the wrong unit (the whole organization when the real
answer lives in one subgroup, or vice versa); mistaking a consensus diagnosis for a
correct one; skipping criterion 5 and leaving the diagnosis unfalsifiable.

**Ethical limits**: diagnosing is not the same as being entitled to decide what
happens next — a diagnosis belongs to whoever will act on it.

**Facilitate within this stage**: ask the client the question they haven't asked
themselves yet, rather than supplying the answer (Schein's Humble Inquiry).

**Transition to Design**: only once all five completion criteria above are met —
not when the practitioner merely feels confident in the diagnosis.

## Stage 2 — Design

**Stage question**: What, specifically, should exist instead — and what is the
smallest version of it worth testing?

**Design does not include the actual launch.** A design that has been attempted is
no longer in this stage; see Launch.

**Input**: a completed Diagnose-stage artifact (bottleneck, unit of analysis,
alternative explanation, falsification criterion already named).

**Actions**: state the intervention as a testable hypothesis; specify the smallest
version of it worth attempting; build the Infrastructure Canvas for it; name what
success and failure would each look like in advance; name the design's ethical
limits; set a boundary **only if this specific design genuinely requires one** —
boundary-setting is not a universal design requirement, and a design that doesn't
need to exclude anyone should not invent an exclusion for the sake of looking
rigorous.

**Concrete artifact**: a written design containing all of the following —

**Design is complete when, and only when:**

1. an **intervention hypothesis** has been stated in the explicit form "if we
   change X, we expect Y" — not a vaguer intention;
2. the **minimum viable intervention** has been specified — the smallest version
   worth attempting, not the fullest version imaginable;
3. an **Infrastructure Canvas** has been filled in for the intervention (routes,
   roles, rhythms, channels, memory — see tool spec below);
4. **expected signals of success and of failure** have both been named in advance —
   not only what success looks like;
5. **ethical limits** specific to this design have been named (who could be harmed,
   excluded, or put at risk by it, and what that costs);
6. **a boundary has been set only if this design actually needs one** — if the
   diagnosis and hypothesis do not require excluding anyone, no boundary should be
   manufactured.

**Typical mistakes**: designing "a pretty diagram no one is behind"; treating
boundary-setting as mandatory even when the specific design doesn't call for one;
stating a hypothesis too vaguely to be falsified; skipping the failure-signal
half of criterion 4.

**Ethical limits**: anyone a design's boundary excludes did not get a vote in that
decision — name this rather than let it disappear into "prioritization."

**Facilitate within this stage**: present the design as a testable bet the client
can reject or amend, not a verdict.

**Transition to Launch**: once the design artifact above is complete. Design ends
here — the first real attempt belongs to Launch, not Design.

## Stage 3 — Launch

**Stage question**: What part of what's needed will only assemble itself during
the action — and did the group turn out to be capable of assembling it?

**Launch begins with an actual, real test** — not a rehearsal, not a plan review.

**Input**: a completed Design-stage artifact, attempted for the first time at real
(if minimal) scale.

**Actions**: run the minimum viable intervention for real; watch for whether roles,
mutual representation, and ordinary courtesy hold once the plan runs out; record
what happened, including a null result.

**A successful launch does not require a Palma Moment.** The absence of a
counter-action is itself a valid, informative result, not evidence the launch
failed procedurally — it may mean the hypothesis was wrong, the timing was wrong,
or the population wasn't ready, all of which are real findings.

**Concrete artifact**: a recorded test result stating what happened, whether it
included an observed Palma Moment or not, and what that implies for the next
decision.

**Launch is complete when, and only when:**

1. the test has actually been run — not merely planned or reviewed;
2. behavior has been recorded — what specifically happened, not an impression of
   how it went;
3. there is a basis to decide whether to keep, change, or stop the intervention.

**Typical mistakes**: assuming a good design removes the need to improvise;
treating the absence of a Palma Moment as automatic failure; declaring success from
attendance or reach numbers rather than an actual recorded behavior; skipping
straight to a second attempt without recording what the first one showed.

**Ethical limits**: people who respond during a launch are not thereby obligated to
keep responding — early participation is not consent to a permanent role.

**Facilitate within this stage**: resist personally taking over and fixing the
launch the moment it wobbles — the group's own capacity to respond is what's being
tested.

**Transition to Transfer**: once a launch result — success, partial result, or
null result — has been recorded and a keep/change/stop decision has a basis. A null
result can still transition to Transfer (the decision may be "stop, and this is why")
or loop back to Diagnose/Design.

## Stage 4 — Transfer

**Stage question**: What, specifically, continues — and is that continuation
actually wanted, or merely assumed to be the goal?

**Transfer does not presuppose independence from the founder as its goal.** A
Transfer-stage result can honestly be any of the following, and none of them is
automatically a failure:

- the action continues, substantially unchanged;
- the action continues partially — some of it, not all;
- the action remains dependent on the center, and this is an accurate, accepted
  description, not a problem to be solved by definition;
- transfer is not needed or not wanted for this particular relationship or system,
  and forcing it would be a mistake.

**Transfer is not a mandatory goal for every tie or system.** Some relationships
and structures are supposed to stay founder-centered; the stage's job is to find
out which, honestly, not to engineer independence everywhere.

**Input**: an effort that has been running long enough to observe what continues
without the practitioner's constant re-initiation.

**Actions**: run a **Handoff Test** (see tool spec — window length is chosen per
system, not fixed); name explicitly what role, if any, the founder still needs to
play.

**Concrete artifact**: a completed Handoff Test result, honestly categorized as one
of the four outcomes above, plus a named (possibly unchanged, possibly null)
founder role.

**Transfer is complete when, and only when:**

1. the test has actually been run, not assumed;
2. the result has been named as one of the four honest categories above, not
   forced into "success" or "failure";
3. the founder's own remaining role, if any, has been stated explicitly.

**Typical mistakes**: assuming continuity without testing it; treating any
founder-dependency as automatically a design failure; institutionalizing a role
that was better left informal, or the reverse; running the test too early, before
the system has had time to settle into its own rhythm.

**Ethical limits**: transfer that happens because the founder walked away, not
because the structure was tested and found capable, is abandonment described as
success — the Method should not let that distinction blur.

**Facilitate within this stage**: name one's own remaining role honestly, including
"none," rather than overstating continued necessity or claiming an untested clean
exit.

**After Transfer**: the cycle does not terminate here. A partial or null Transfer
result is itself new diagnostic information and can loop back to Diagnose.

## Facilitate — the cross-cutting principle (not a stage)

**Governing question, present at every stage**: am I increasing what this person or
group can see and decide, or am I deciding for them?

**How it shows up per stage**: Diagnose — asking rather than telling (Humble
Inquiry); Design — presenting the design as a testable bet, not a verdict; Launch —
resisting the urge to personally rescue a wobbling launch; Transfer — naming one's
own role honestly rather than either overstating necessity or claiming an untested
exit.

**Why it is not stage 5**: it has no artifact or completion criterion of its own
that is distinct from the stage it's operating within — there is no separate
"Facilitate is done" moment the way there is a completed diagnosis or a recorded
launch result. Chapter 20's material (built on the Bombom case) works as an
illustration precisely because that case isolates the principle cleanly — the
author had no authority to decide anything there — not because Facilitate is a
fifth thing that happens after Launch.

**Ethical core**: the temptation to slide from process facilitation into deciding
for someone is strongest exactly when stakes are highest and the outcome matters
most personally to the practitioner — this is stated, not merely implied, in how
the principle should be written up.

## The five tools

### 1. Relationship Capital Map

**Purpose**: locate, at the right unit of analysis, where a specific relationship
or network is strong or weak, using two distinct layers rather than one flat list —
because a network is not simply the sum of its individual ties, and treating it
that way hides exactly the information a design decision needs.

**Dyadic layer** (properties of one specific tie): **trust, reciprocity, access,
tie strength.**

**Network layer** (properties that only exist at the level of the network itself,
not any single tie): **structure, bridges, redundancy, bottlenecks.**

**Do not draw the network as a property of one relationship.** A single tie can be
high-trust and still leave the surrounding network with a single point of failure;
the two layers must be assessed separately and neither substitutes for the other.

**User-facing questions — dyadic layer**:

- *Trust*: what has this person already been safe to hand you, or you to them?
- *Reciprocity*: name one specific thing given and one specific thing received —
  not an impression, a remembered episode.
- *Access*: is there an actual working channel to this person right now, likely to
  be used if you reach for it?
- *Tie strength*: **use only signals supported by a registered source; do not
  automatically treat duration, multiplexity, and dormant-tie reactivation as
  interchangeable.** Specifically: (a) *contact frequency/pattern* is Granovetter's
  own operationalization of tie strength (SC-004) — but his own finding is that
  frequent, close ties often carry *less* novel value than infrequent ones, so
  frequency indicates closeness, not usefulness; (b) *dormant-tie value* is a
  separate, independently registered phenomenon (Levin, Walter & Murnighan 2011,
  SC-090) — a tie that has gone inactive for years can retain or even exceed active-tie
  value on reconnection, which means duration-since-last-contact does *not*
  predict current value the way it might seem to; (c) **multiplexity (interacting
  across multiple contexts or roles) has no dedicated registered source in this
  project's corpus** and should not be asserted as a validated tie-strength signal
  until one is sourced — flag rather than use.

**User-facing questions — network layer**:

- *Structure*: if this one relationship or role disappeared, what else in the
  reachable network would disappear with it?
- *Bridges*: who, if anyone, connects two otherwise-separate clusters — and is that
  bridge a single point of failure?
- *Redundancy*: are there multiple independent routes to the same information,
  access, or help, or exactly one?
- *Bottlenecks*: where does the network's actual capacity to act concentrate, and
  does that match where the organization assumes it concentrates?

**Observable signs**: a concrete episode recalled only after being prompted (not
volunteered spontaneously) often reveals more real reciprocity than a person's own
general self-assessment; a "who would you contact for X" test produces a countable
number, not a feeling.

**Interpretation limits**: a person's *stated* connectivity systematically differs
from their *demonstrated* connectivity — always ask for the episode. A dense
personal network around one individual (dyadic strength) does not mean the
surrounding network has redundant access (network-layer property) — these are two
different, non-substitutable measurements.

**TAK.Shtab example** (verified, SC-049): dyadic — trust: the residents' association
tolerated the unauthorized basement occupation without being asked; reciprocity:
two body-armor vests from friends in Israel, used personally then passed to friends
at the front; access: the contact network grew "roughly exponentially" as each new
volunteer multiplied reach. Network layer — structure/bottleneck: by 2023 the
organization's funding and program delivery no longer concentrated solely in the
founder's personal network; bridges: the pre-war community (publishing house, think
tank, recurring Friday gathering) plausibly seeded the 2022 mobilization's initial
contacts, per the author's own account — a bridge from an unrelated prior context
into the new effort.

**Confirmed TCF observations only** (each stated as a single interview's finding,
not a property of TCF): in SC-097 (Anya), a class member volunteered on the spot to
co-sign a residency document, mid-class, without being asked twice — one instance
of dyadic trust. In SC-095 (Francisco), a participant who initially denied any
functional exchange had, on being asked about a specific episode, in fact lent a
microphone and independently organized a trip itinerary for several members — one
instance of understated dyadic reciprocity. In SC-097, an operational "who would
you message" test produced 14-16 names; in SC-095, 3 names; in SC-099 (the
low-regularity case), effectively 0 new gym-formed contacts — three separate
individual results from three separate interviews, not a distribution to be
averaged. In SC-098 (Luciana), one member reported reactivating a 2019 acquaintance
with the founder that had produced no connection at the time — one dormant-tie
account from one interview. In SC-095 and SC-096 (Francisco, Rami), two separate
members independently guessed that a shared design feature (small in-class
subgroups) arose from a space/equipment constraint — two individual guesses that
happen to converge, not a confirmed structural fact about TCF's design.

**What cannot be claimed**: this is not a validated psychometric scale — no item
generation, reliability testing, or independent sample stands behind it. The
dyadic/network distinction is an organizing device for field use, not a
scientifically established two-factor model.

### 2. Infrastructure Canvas

**Purpose**: make visible the five concrete, changeable elements that let
interaction continue without the organizer personally re-initiating it each time.

**Elements, each with a distinct function and its own observable sign** (verified
against the current manuscript's own use of these five — no element duplicates
another's function):

| Element | Function | Observable sign |
|---|---|---|
| **Routes** | how people actually find or reach each other | a route is real when it is used without the organizer brokering the specific instance |
| **Roles** | what a participant can *do* here beyond receive or watch | a role is real when someone performs it without being asked a second time |
| **Rhythms** | what repeats on its own schedule | a rhythm is real when the next occurrence doesn't require a fresh invitation |
| **Channels** | where interaction actually happens | a channel is real social infrastructure when people use it without the organizer present — its mere existence and membership count are not sufficient evidence |
| **Memory** | what a returning or new participant doesn't have to be told again | memory is real when the group, not only the organizer, carries and applies it |

**Interpretation limits**: the presence of a channel is not evidence it functions as
relationship infrastructure — check directly, since participants sometimes
explicitly report a channel doesn't work that way for them.

**TAK.Shtab example** (verified, SC-049): routes — convoy routes coordinated with
the military at each checkpoint, refined over at least four missions; roles — a
duty roster and request-tracking system, plus the informal "CBO" (Chief Box
Officer) role that stayed informal versus a second role that became paid and
formal; rhythms — the recurring three-wave research study; channels — the shift
from word-of-mouth requests to the formal Taktion program; memory — a pre-war
domestic-violence research study reactivated for the 2023 narrowing decision.

**Confirmed TCF observations only**: channels — in SC-096 (Rami), one member
stated the booking app is not used for social purposes ("I don't go there for
people"); in SC-096 and SC-098 (Rami, Luciana), reception coffee and a Saturday
team-format session were separately named as mechanisms that bring members
together. Rhythms — in SC-099, the low-regularity participant's own pattern (one
weekly group class plus solo, headphone-wearing open-gym sessions) co-occurred with
zero new gym-formed connections in her account; her own biography (school group
projects vs. shared hallways) independently supports the same distinction in the
same interview. **Roles and memory have no confirmed TCF example in the current
interview set** — state this plainly rather than inferring one.

**What cannot be claimed**: these five elements are not presented in the literature
as a single validated model of "relationship infrastructure" — this is the book's
own operational grouping, built on established adjacent literatures, not itself
independently validated.

### 3. Response Signals

**Purpose**: replace a single yes/no question ("is there a relationship?") with a
set of observable behaviors a practitioner can check for — **not a maturity ladder,
not a sequence every relationship must climb.**

**Signals** (nonlinear — no implied order, no rung numbering): **responds, returns,
helps, connects, coordinates, takes responsibility.**

**These are not stages of relationship maturity.** Different systems need different
signals depending on what they're actually for — a relationship that only ever
reaches "helps" is not a lesser version of one that reaches "coordinates"; the
absence of a "higher" signal is not, by itself, a failure. A practitioner should
check for whichever signals matter to the specific question being diagnosed, not
assume all six are the goal for every relationship.

**User-facing questions**: has this person responded when reached? Have they
returned without a fresh invitation? Have they ever helped, unprompted? Have they
introduced you to someone else, or vice versa? Have you seen them coordinate with a
third party on your behalf, without you present? Has anyone taken visible, ongoing
responsibility for a piece of this without being asked to?

**Observable signs**: each signal should be answerable with a specific remembered
instance, not a general impression.

**Interpretation limits**: a relationship or system does not need to exhibit every
signal to be valuable, and exhibiting a "later" signal does not retroactively prove
the "earlier" ones were present in the way a ladder model would imply — treat each
signal as an independent check, not a cumulative score.

**TAK.Shtab example** (verified, SC-049): responds/returns is directly documented
in the founding sequence — "first a small delivery, then a larger one, then cars,"
a real, dated escalation. Takes responsibility is documented concretely: one
volunteer's role moved from "showed up to help" to operational responsibility to a
paid position, with no single formal handoff moment.

**Confirmed TCF observations only**: responds/returns/helps/connects are each
directly supported by at least one interview (the co-signing episode for helps; the
microphone/itinerary episodes for helps and connects). **Coordinates and takes
responsibility have no confirmed example in the current TCF interview set** — say
so plainly if the tool is illustrated with TCF material.

**What cannot be claimed**: this is not a validated model with empirically
established transition probabilities between signals — it is an observational
checklist. Do not imply that observing one signal predicts observing another.

### 4. Palma Moment

**Purpose**: name the specific, observable instance when one side's action is met
with a genuine counter-action that changes subsequent interaction — the smallest
visible unit this book treats as a relationship actually forming or strengthening
in real time.

**Definition, precisely stated**:

A Palma Moment is **the first significant, observed instance of a counter-action
that changes what happens next between two sides.**

- It **can** occur after an invitation or a request — it does not have to arise
  unprompted to count.
- It is **not required to be fully spontaneous.**
- It is **not equivalent to any response** — a reply, an acknowledgment, or a
  polite reaction is not automatically a Palma Moment; the counter-action has to be
  significant enough to actually change what either side now expects from the next
  interaction.
- It is **not a scientifically confirmed developmental stage** — it is the author's
  own diagnostic naming device for a real-time event to watch for, not a claim
  about an independently validated psychological mechanism.
- It is **not guaranteed to occur at every launch.** A launch with no observed
  Palma Moment is not thereby a failed launch (see Stage 3 above) — its absence is
  itself information.

**User-facing questions**: what did one side actually do? What, specifically, did
the other side do in response? Would this have happened without the first action?
Is there evidence the response changes what either side now expects from the next
interaction?

**Observable signs**: a concrete, nameable action met by a concrete, nameable
counter-action — not goodwill merely expressed.

**Interpretation limits**: a single Palma Moment is not yet Relationship Capital —
capital accumulates when a *history* of such moments raises the likelihood of the
next one. One good exchange demonstrates the mechanism is possible, not that it
will recur.

**TAK.Shtab example** (verified, SC-049): the first delivery — "a small delivery, a
box, maybe two" — arriving in response to the newly opened headquarters, before any
system existed to solicit it, is the organization's founding Palma Moment.

**Confirmed TCF observations only**: the residency co-signing episode (SC-097) and
the microphone/itinerary episodes (SC-095) both meet the definition — a specific
need was stated, and a specific counter-action answered it, changing what each
party could subsequently expect from the other.

**What cannot be claimed**: do not present the Palma Moment as "the moment a
relationship scientifically begins," a validated psychological construct, or
equivalent to any named academic stage-model of relationship formation.

### 5. Handoff Test

**Purpose**: convert "the founder is less needed now" from a feeling into a tested
result — what, concretely, keeps happening without the organizer's continued,
personal initiative.

**Window**: **not a fixed universal period.** The observation window should be
chosen based on the system's own natural rhythm — a weekly-cadence group needs a
different window than a system that operates on a monthly or seasonal cycle. Stating
a single fixed number (e.g., thirty days) for every system would misrepresent the
test as more standardized than it is.

**The test asks**:

- what continued;
- who initiated it;
- which of the Infrastructure Canvas elements (routes, roles, rhythms, channels,
  memory) survived;
- what stopped;
- where the center is still necessary;
- **whether transfer was actually desirable here at all** — not assumed to be the
  goal.

**Observable signs**: a real pass requires an actual, deliberate reduction in the
organizer's initiation during the chosen window — the test is only informative if
run, not imagined.

**Interpretation limits**: a result showing nothing continued is not proof the
effort was worthless — it may mean the test was run too early, or that
center-dependency was, for now, the right design for this particular system. A
result showing full continuation does not certify permanence beyond the window
observed.

**TAK.Shtab example** (verified, SC-049/SC-110): by 2023-2024, the organization had
roles, instructions, salaries, and donor-reporting obligations that did not depend
on the founder's daily personal initiative — independently corroborated by the
organization's own public communications (SC-110), not the founder's account alone.
**This is a retrospective example of features consistent with a passed handoff —
no formally designed, dated Handoff Test was actually conducted for TAK.Shtab, and
the manuscript must not state that one was.** The claim should stay at "by 2024
the structure showed these features," not "a Handoff Test was performed."

**Confirmed TCF observations only**: **no TCF interview documents an actual handoff
test being run.** Several participants' accounts bear on what a test's *result*
might show if run — in SC-095, Francisco predicts almost nothing would change
without Miguel for three months; in SC-096, Rami predicts the gym would continue
but become "less personal, less social, less fun"; in SC-097, Anya predicts she
would miss Miguel but the workouts and other relationships would remain — but each
of these is one participant's own prediction, not an observed test result, and must
be labeled as such if used.

**What cannot be claimed**: no fixed time window is empirically derived or
optimal — the window is a practical choice tied to the system's own rhythm, stated
explicitly whenever the tool is used. A passed test does not certify durability
beyond the window actually observed.

## Standing epistemic notes (apply to all five tools)

- None of the five tools is a validated scientific scale, instrument, or
  empirically-tested model. Each is a practitioner/field tool built on established,
  individually-cited research, not itself independently validated.
- The Collective Fitness is, throughout, a **developing field case**, not a
  controlled study. **Every TCF-sourced claim in this document is written as a
  finding from one specific, named interview — never as a general property of "TCF"
  or "TCF members."** Where two interviews happen to converge (as with the
  small-subgroup design guess), this is stated explicitly as convergence between two
  individual accounts, not as corroborated fact.
- TAK.Shtab remains the one case in this project independently corroborated by a
  primary source outside the author's own testimony (SC-110) — this should continue
  to be stated plainly wherever it is used, and just as plainly bounded: corroborated
  on the institutionalization facts specifically, not on every detail of the
  founder's personal account.
